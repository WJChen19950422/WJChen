# 使用者測試紀錄分析與 R4 修正 — 2026-11-06

## 資料與分段

來源為使用者提供的 UART JSONL 與 telemetry CSV，涵蓋約一小時、多段操作。
本報告只使用有完整電流封包的近期片段，以實際限流寫入活動分段，沒有把
整份檔案都視為連續拖動。時間皆為 Asia/Taipei (+08:00)。
原始上傳檔未加入來源交付；以下是分析摘要。

UART 記錄時間戳來自 PC GUI Log，含 USB／作業系統與訊息派送延遲，並非
邏輯分析儀的線路時間；因此無法將每筆 RTT 全部歸因於 MCU 執行時間。

寫入區間共有 396 個可比較的相鄰回覆間隔，150 個間隔包含一筆 0x06
寫入。含寫入的間隔平均 88.31 ms、P90 117 ms；其他間隔平均 62.50 ms。
這段的 0x06 ACK 中位數 57 ms、P90 58 ms。ACK 後通常約 1 ms 就送出
下一筆電流請求，顯示 prior Responsive 版本確實已在穿插電流讀取。

具體一例：

```
11:47:13.339  上一筆電流 RX
11:47:13.370  0x06 TX              （先經過 31 ms）
11:47:13.427  0x06 ACK             （再經過 57 ms）
11:47:13.440  下一筆電流 RX         （再經過 13 ms）
```

總間隔 101 ms = 31 + 57 + 13。因此，主因有具體通訊／排程等待證據；
不需要用滑桿或儀表固定刷新慢來解釋這一筆停頓。
單看此紀錄仍不能把 57 ms 分拆成 MCU 參數處理、USB-UART 緩衝與 OS 延遲。

CSV 是原設計約每秒取一筆記錄，這份中位數為 1061 ms；它不是逐筆 UART
或逐幀畫面的資料，不能以 CSV 列間距判斷 UI 更新率。

## R4 改動

1. **慢寫入前的預讀**：若預估 ACK 完成時間會跨過下一次監控期限，就先
   讀一次電流，縮短「上一筆樣本已經變舊，才開始慢寫入」造成的間隔。
   首次預估 60 ms，後續採最近一次成功 0x06 的實際耗時。
2. **避免多餘讀取**：剛收到電流（5 ms 內）不重複讀；使用者設定 500/1500 ms
   等較慢週期也不會被無條件快速輪詢覆蓋。
3. **高解析度時間**：Demo 交易／排程與 GUI 電流刷新間隔使用 perf_counter。
   原紀錄大量 0、15、16、31、63 ms 跳階有計時解析度疑慮；不再把 0.0 ms
   視為真正的零傳輸時間。安全 deadline/heartbeat 原有 monotonic 邏輯保留。
4. **Qt PreciseTimer**：監控與目標合併計時器使用 Qt 支援的高精度類型；
   作業系統忙碌或 MCU 較慢時仍可能延後，不能保證每 50 ms 成功。
5. 品牌列及視窗顯示 v0.18 R4，以辨識解壓縮後真正執行的版本。

## 軟體驗證與限制

最終完整套件：180 passed, 9 subtests passed in 62.13s，exit 0。
完整測試輸出見 pytest.txt；Python compileall exit 0，輸出見 compileall.txt。
新增四個案例驗證慢 ACK 前預讀、無重複新鮮樣本、較慢週期受尊重及精準計時器。

`prewrite_simulation.json` 以讀取 14 ms、ACK 57 ms 的固定假延遲比較：

| 模擬項目 | prior Responsive | R4 |
|---|---:|---:|
| 相鄰電流樣本最大間距 | 85 ms | 71 ms |
| 整筆限流完成時間 | 169 ms | 183 ms |
| 同時 UART 請求 | 1 | 1 |

多讀一筆電流會增加整筆設定完成時間，改善的是監控連續性；本次未聲稱限流
生效更快，也未聲稱實機達到 71 ms。R4 尚未經使用者 Windows／MCU 重測。

0x06 若確實等待約 57 ms，之後再讀電流需約 13–14 ms，同一 UART 的同步
交易就可能形成約 70 ms 間隔。要保證寫入期間仍持續低於 50 ms，需要先縮短
實際 ACK 等待或修改 MCU／通訊機制；這超出本 PC UI 範圍，未擅自修改。

Device Code、故障、原參數、過載檢查、寫入 ACK、讀回、STOP／學習及兩秒
原有限制均保留。MCU 韌體、UART Protocol、Checksum、Flash 未改動。

## 實機重測

開啟 R4（確認視窗／品牌列有 R4），勾選自動監控、週期 50 ms。
先關閉輪詢封包紀錄比較不拖／拖動的刷新間隔；若仍需分析，再短暫開啟
封包紀錄，取得同樣的 UART Log。不要只用 CSV 的一秒記錄間距判定刷新率。
